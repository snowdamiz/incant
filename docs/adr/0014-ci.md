# ADR 0014: GitHub Actions and target-specific runnable probes

Date: 2026-10-08. Updated: 2026-10-11. Status: decided by director instruction
in the PLAN.md revision 5 decision record. This does not approve the Phase 0
gate or claim later-phase work is implemented.

## Decision

Use GitHub Actions for repeatable builds and nightly target artifacts. Pin action revisions, Rust, Node dependencies and Cargo resolutions. Dedicated live-eval secrets are only exposed to a manually invoked protected evaluation job. CI never invokes coding agents. Service and multi-client integration tests run on Linux runners against PLAN.md's local service stack (section 2.7), which needs no cloud, identity or store credentials; hosted services are reserved for jobs whose gates need the real one.

## Development and checkpoint cadence — director decision 2026-10-11

The director authorized local verification plus fast main checks, and comprehensive
CI in periodic main-to-release batches. PR82's measured workflow-to-macOS-completion
was 42m41s (37m21s execution). Recent reviewed PR89–93 fast development jobs
took **109–133 seconds** to execute
and **1–2 seconds** in queue. This measures the narrower per-merge gate after local
validation; it does not mean full Rust/platform compilation became that fast.
[Exact job/head/timing evidence](../spikes/evidence/fast-main-checks-2026-10-11.json)
preserves the five successful runs. Comprehensive release validation remains
separate and has exposed platform defects that are repaired on main.

- `main` is the development branch. Before a PR, run all applicable locally feasible
  checks: observable behavior tests, fmt/Clippy, generated contracts and dependency
  checks where affected, plus native or visual acceptance when needed. Record exact
  commands/results and any unavailable platform evidence in the PR. Review the
  diff. The required hosted `development-checks` job runs Python/Node tool tests,
  conventions, formatting, SDK/bridge checks, and the UI production build and tests;
  it does not compile Rust or run the full platform matrices. It runs on main pushes
  and PRs targeting main. Local failures still block merge.
- `release` is the last comprehensively checked integration baseline. Bootstrap it
  from an existing all-green main integration and record that provenance. Protect
  it with the full check contexts listed in `.github/release-checks.json`. No release
  tags, packages, signing or distribution uploads are implied.
- Every three hours, if main has changes beyond release and no checkpoint is active,
  the single integration owner updates the persistent `codex/release-candidate`
  branch. Start from its prior head (or main for the first checkpoint), merge the
  current release and main histories without rewriting published history, and verify
  that the candidate tree exactly equals the selected main tree. Unexpected content
  differences require reconciliation in main before proceeding. Record main, release,
  candidate and tree SHAs in the PR. Open one candidate-to-release PR and freeze its
  head while testing; do not stack checkpoint PRs.
- Every candidate push triggers the complete general, desktop, credentials, Wasm,
  physics, six-platform and website suites, without path filtering. The general
  classifier is forced to `full`, including documentation-only batches. Workflows
  also permit manual diagnosis. Opening the release PR does not trigger a duplicate
  matrix. Subsequent main pushes neither update the candidate nor cancel its runs.
  The stable candidate ref retains reusable dependency caches across batches.
- Require successful latest-head results for every listed context, not skipped,
  cancelled, missing or pending results. Review the integrated diff and merge the
  exact candidate into release with `Built-by: astra` in the merge body. Verify the
  resulting tree matches the checked tree. The release merge itself does not rerun
  an identical full suite. Main's fast check and release's full checks are separate
  branch requirements; do not make main wait for release.
- If a checkpoint fails, diagnose it and make reviewed, locally verified fixes in
  main. Hold release. After the current run is terminal (or deliberately cancel its
  now-obsolete work), update the same candidate from main and rerun the full suite.
  Never erase a failure by dropping a required context or force-pushing. Keep a
  known failing change out of subsequent development work where it would invalidate
  testing; do not silently accumulate failures across checkpoints.
- The thread heartbeat coordinates the three-hour cadence, remains quiet when
  unchanged and reports meaningful failures or promotion. Continue useful local
  implementation while a checkpoint runs. Only the integration owner writes shared
  main/release/candidate refs, and at most two independent reviewed development PRs
  should be ready at once; dependent work remains local until its parent merges.

Website-only main changes retain automatic Pages build/test/deployment through a
path-filtered caller; candidate validation never deploys Pages. The former nightly
six-platform build is included once per checkpoint, without a duplicate daily
matrix. Future real-device, service soak, security, licensing and performance gates
in the plan remain required; this policy does not claim they are implemented.
Live account evaluation remains explicitly invoked with protected credentials.
Hosted simulator builds still do not satisfy physical-device performance gates.

## Historical evidence and implementation boundary

Desktop, WASM, iOS and Android hosts share incant_platform_smoke. Local macOS, browser and iOS simulator execution is measured. The private remote is snowdamiz/incant. All six PR-triggered target builds have passed, with desktop, browser and iOS simulator execution. Android 35 x86_64 hosted emulator execution also passed: Activity startup and instrumentation both ran the native document/120-tick probe (see docs/spikes/evidence/android-emulator-2026-10-08.json). This is not physical-device or visual evidence. Real-backend synthetic credential persistence across changed executables passes on all three desktop hosts. Nightly artifact history and signing remain pending.

## Consequences and revisit trigger

Development/debug artifacts are not signed distribution releases. Director-managed Apple/Windows certificates, hosted or self-hosted runner provisioning, Android SDK licenses and hosted real-device access in AWS Device Farm must precede release gating. Signing certificates are first needed for Phase 5 store uploads, not Phase 0. Self-hosted runners must never run untrusted fork code with signing/eval credentials.
