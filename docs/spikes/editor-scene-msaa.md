# Ordinary editor scene MSAA

Source draft; native compilation, Metal numerical execution and appearance review are pending. This does not pass a Phase 1 or device performance gate.

The ordinary editor viewport explicitly constructs `Renderer::new_with_scene_msaa(..., 4)`. Existing `Renderer::new`, `headless` and `new_with_gpu_timing` retain their 1x default. Pixel-grid cameras select 1x with their existing nearest display mapping. Retained native/dynamic-resolution/temporal submits explicitly select 1x, including vendor upscale routes; they do not inherit editor sampling.

The cold constructor admits only 1 or 4 samples. A 4x request checks adapter `Rgba16Float` render/4x/resolve and `Depth32Float` render/4x support before requesting the device or allocating renderer resources. Unsupported modes/capabilities fail with `SceneMsaaError`. SSAO with the 4x renderer refuses before preparing its resources because this slice has no depth resolve. There is no silent quality fallback or alpha-to-coverage.

At cold startup, the 4x renderer prepares both 1x and 4x variants for diagnostic geometry, all twelve material alpha/cull/mirror combinations, sprites and world text: thirty world pipelines instead of fifteen. Shadows, output, UI and chrome retain their existing one-sample pipelines. Draw preparation only looks up the finite world catalog; this explicitly increases cold compilation work and does not claim a measured startup or frame-time result.

A frame uses 4x linear HDR color and 4x depth through diagnostics, opaque/MASK and BLEND models, sprites and world text. One hardware color resolve runs after the last world draw and before bloom/display conversion. The graph and GPU profiler have an explicit `SceneResolve` interval; it is absent at 1x. Depth stays multisampled and is neither sampled nor approximated. Continuous world varyings use centroid interpolation, while flat values remain flat. The four corresponding cooked shader contracts are versioned independently and reject center/sample mismatches; shadow/UI contracts stay strict. Cooked flags continue to select private cooked artifacts rather than runtime WGSL fallback. The [GPUWeb multisample contract](https://gpuweb.github.io/types/interfaces/GPUMultisampleState.html) and [WGSL interpolation contract](https://www.w3.org/TR/WGSL/#interpolation) define the underlying sampling rules.

The cache key includes size and sample count. The existing 1x policy retains twelve logical bytes per pixel, a 192 MiB idle-frame limit and a 16 MP ceiling. The explicit 4x policy retains fifty-six bytes per pixel (32 HDR, 16 depth, 8 resolved HDR) with a 512 MiB idle-frame limit and the same 16 MP ceiling. The byte cap therefore reduces its effective pixel ceiling to about 9.58 million pixels. A 3840x2160 frame accounts for 464,486,400 bytes (about 443 MiB). Checked sizes/arithmetic are validated before attachment allocation. These numbers exclude driver padding, caller output, other renderer resources and queued old textures; they are not aggregate GPU memory bounds. Encoded commands continue to retain their old attachment owners across cache replacement.

CPU controls cover unknown counts, missing usage/sample/resolve capability, AO refusal, checked dimensions/byte caps, graph ordering and emitted cooked centroid decorations/mismatch refusals. Four ignored native-GPU controls cover isolated 320x240 ordinary diagnostic cube 1x/4x silhouettes for pixel review; the mixed world pass families and depth; queued resize, clear, refusal retention and retained/pixel-grid 1x compatibility; and real post-text/pre-display resolve timestamps. Their optional immutable RGBA receipts use `INCANT_SCENE_MSAA_EVIDENCE`; PNGs use the existing `INCANT_HDR_EVIDENCE`. A separate actual Metal run and rendered-pixel review are required before calling the editor appearance verified.
